# 2026-07-31

### 修复

- **模型价格补齐缓存创建 / 缓存读取定价（拉取 → 展示 → 计费全链路）**：缓存命中率高的会话算出来的
  成本几乎是 0，例如这段 `message_delta`：

  ```
  "usage":{"input_tokens":2,"cache_creation_input_tokens":838,
           "cache_read_input_tokens":54773,"output_tokens":15}
  ```

  按老逻辑 `claude-opus-4-6` 只收 $0.000385（只有 2 个 input token + 15 个 output token 计了钱），
  55611 个缓存 token 全部按 0 单价计费。

  **根因在拉取阶段**：models.dev 的 `api.json` 是 `{ provider: { models: { modelId: {...} } } }`，
  同一个裸模型 ID（`claude-opus-4-6`）同时挂在 176 个 provider 下，而 `fetchModelsDevData()` 直接
  `pricingMap.set(modelId, cost)` 一路覆盖 —— 最后遍历到谁就用谁。实测 2652 个有价模型里有 **1606 个**
  最终落到了一个连 `cache_read` 字段都没有的二级经销商条目上（`claude-opus-4-6` 落到 `jiekou`
  的 `{input:5, output:25}`，`claude-haiku-4-5` 落到 `cortecs`），缓存单价直接缺失按 0 处理；
  个别渠道甚至挂着 `{input:0, output:0}` 的占位价，会把整条价格冲成 0。

  修复分四处：

  - **拉取（`src/model-catalog.ts`）**：新增 `buildCatalogMapsFromModelsDev()`，同一模型 ID 的多个
    provider 条目改为**择优**而非覆盖 —— 按「官方/一方 provider 优先 → 有真实价格优先（`input=output=0`
    的占位条目排最后）→ 缓存字段完整优先」打分，同分保持 models.dev 原顺序；选中条目若缺
    `cache_read`/`cache_write`，再从**基础价格完全一致**的其他 provider 条目回填（价格不一致的不回填，
    避免用别家的折扣价污染）。同时对 `cost`/`limit` 做数值校验，非数字、负数、缺 `output` 的条目直接丢弃。
    context window 走同一套择优逻辑。修复后 `claude-opus-4-6` 恢复为
    `{input:5, output:25, cache_read:0.5, cache_write:6.25}`，缺 `cache_read` 的模型从 1606 降到 1487
    （剩下的是上游确实没有缓存能力的模型）。

  - **持久化（`src/catalog-db.ts`）**：`saveCatalogToDb()` 的 `onConflictDoUpdate` 把 `set` 写成了
    `contextWindow: modelCatalogCache.contextWindow`，编译出来是**已存在行的列引用**，等于把旧值写回自己
    —— 冲突时整行原地不动，连 `fetchedAt` 都不更新。这意味着一旦库里存过一份坏价格，24h 定时刷新
    永远不会生效。改为引用 `excluded.*`（本次插入的新值）。

  - **计费（`src/pricing.ts`）**：
    - 上游没给缓存单价时不再按 0 计费，改为按官方比例从 input 单价推导兜底：cache read = 0.1x input，
      5m cache write = 1.25x input，1h cache write = 2x input；OpenAI 的 cached input 同样 0.1x input
      且不收缓存写入费。是否用了兜底价通过 `cache_pricing_derived` 标记出来。
    - Anthropic 缓存写入按 TTL 分档计费：`cache_creation_input_tokens` 用已经落库的
      `ephemeral_5m_input_tokens` / `ephemeral_1h_input_tokens` 拆成两档，1h 档按 1.6 倍于 5m 的单价计算
      （之前 1h 缓存一律按 5m 价，少收 1.6 倍）；上游没上报拆分时全部按 5m 档。
    - `CostBreakdown` 新增 `cache_write_5m_tokens`/`cache_write_1h_tokens` 和实际计费用的
      `cache_read_price`/`cache_write_5m_price`/`cache_write_1h_price`。
    - `console-store` 的用量聚合与时间序列成本统计补上 `ephemeral_5m/1h` 字段，与单条请求详情口径一致。

  - **展示（console 前端）**：Models 页表格补上「缓存读取价格 / 1M」「缓存写入价格 / 1M」两列，
    价格格式化对小于 1 的单价保留有效位（原先固定两位小数会把 $0.03 抹成 $0.03/$0.00）；
    日志详情的成本公式改用后端返回的**实际计费单价**（兜底价会标注「（推导）」），保证
    「单价 × token 数 = 成本」在页面上自洽，1h 缓存写入会额外拆成 5m / 1h 两行公式。

  修复后同一条请求 `claude-opus-4-6` 的成本从 $0.000385 变为 $0.033009
  （input $0.000010 + output $0.000375 + cache read $0.027387 + cache write $0.005237）。
